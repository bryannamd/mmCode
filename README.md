# mmCode

**밀리미터 단위로 일하는 코딩 에이전트 절차.** Claude Code와 Codex에서 같은 이름으로 부르는 스킬 묶음입니다. 코드를 고치기 전에 무엇을 이해했는지 먼저 보여 주고, 계획을 세우고, 시험으로 확인한 뒤에 끝났다고 말합니다.

> Work in millimeters. Explain, plan, pair, relay, check, prove.

---

## ⚡ 지금 바로 쓰는 가장 쉬운 방법

설치 두 줄, 사용 한 줄입니다. 나머지는 몰라도 됩니다.

**1. 설치합니다.** 터미널에서 한 번만 실행합니다.

```sh
claude plugin marketplace add bryannamd/mmCode
claude plugin install mmcode@mmcode
```

**2. 프로젝트 폴더에서 Claude Code를 켭니다.** 그리고 `/go` 뒤에 하고 싶은 일을 평소 말투로 적습니다.

```text
/go 로그인 버튼을 눌러도 아무 반응이 없어. 고쳐 줘.
```

**3. 끝입니다.** 이제 Claude가 이 순서로 움직입니다.

1. 어떤 종류의 일인지 고르고 `▶ 경로: 버그 수정`처럼 한 줄로 알려 줍니다.
2. 코드를 고치기 전에 "작업 이해" 화면을 보여 줍니다. 무엇을 어떻게 고칠지 미리 알 수 있습니다. 작은 수정이면 두 줄로 줄입니다.
3. 고치고, 시험을 돌리고, "작업 완료" 화면으로 결과를 보고합니다.
4. 커밋은 혼자 하지 않습니다. 끝나면 "커밋할까요?"라고 묻습니다.

막히면 아래 **단계별 사용법**을 보세요. 먼저 설치가 잘 됐는지 보려면 `/probe`를 입력하면 됩니다. 표식 한 줄이 나오면 정상입니다.

## 이게 무엇인가요

mm은 밀리미터입니다. 자에서 가장 작은 눈금이고, 눈대중과 측정을 가르는 단위입니다. 코딩 에이전트도 그렇게 일해야 한다고 봅니다. 크게 짐작해서 한 번에 밀어붙이지 않습니다. 이해한 내용을 먼저 말하고(explain), 계획을 세우고(plan), 긴 일은 단위로 쪼개 넘기고(relay), 변경이 닿는 범위를 재고(check-impact), 수치를 믿기 전에 점검하고(check-benchmark), 증명을 남깁니다(make-verifier).

m²로 읽어도 됩니다. 변경 하나가 덮는 면적을 먼저 재는 습관이 이 묶음의 절반입니다.

## 들어 있는 스킬

| 이름 | 하는 일 | 이렇게 말하면 됩니다 |
|---|---|---|
| `go` | 작업 입구. 요청을 읽고 경로 18개 중 하나를 골라 그 절차를 연다 | `/go <하고 싶은 일>` |
| `explain` | 코드를 고치기 전에 "작업 이해" 화면으로 이해한 내용과 범위를 먼저 보여준다 | `/explain <하고 싶은 일>` |
| `plan` | 계획자·일꾼으로 나눠 계획하고, 엄격한 시험과 교차 검토로 실행한다 | `/mmcode:plan <하고 싶은 일>` |
| `pair` | 다른 코딩 에이전트(codex·agy)에 코딩을 맡기고, 이 세션은 계획·검증을 맡는다 | "codex한테 시켜", "agy로 구현해" |
| `relay` | 큰 작업을 단위 표로 쪼개 브리프 → 작업 → 검수 → 커밋 → 인계 순서로 세션을 넘기며 이어 달린다 | `/relay <작업 설명>` |
| `check-impact` | 작은 변경이 diff 밖 어디를 깨뜨릴 수 있는지 찾고, 안전한 이유를 실행으로 증명한다 | "이 변경이 뭘 깨뜨릴 수 있어?" |
| `check-benchmark` | 성능 수치를 보고하거나 그 수치로 결정하기 전에 7가지 질문으로 점검한다 | "진짜 빨라진 거 맞아?" |
| `make-verifier` | 프로젝트 전용 검증 스킬을 만든다. 동작 모드(`verify-<app>`)와 형식 모드(`prove-<area>`)가 있다 | "검증 스킬 만들어 줘" |
| `probe` | 설치 확인용. 표식 한 줄을 출력하고 멈춘다 | `/probe` |

흐름은 이렇습니다. `go`가 경로를 고르고, 코드를 바꾸는 경로면 `explain` 화면을 먼저 띄운 뒤 `plan`이 계획하고 실행합니다. 길어지면 `relay`로 세션을 넘기고, 코딩 상대가 있으면 `pair`로 맡깁니다. 변경 영향이 걱정되면 `check-impact`로, 성능 수치를 말하기 전에는 `check-benchmark`로 점검합니다. 같은 증명을 반복해야 하면 `make-verifier`로 프로젝트 전용 검증 스킬을 남깁니다.

## 설치

### Claude Code

```sh
claude plugin marketplace add bryannamd/mmCode
claude plugin install mmcode@mmcode
```

### Codex

```sh
codex plugin marketplace add https://github.com/bryannamd/mmCode
codex plugin add mmcode@mmcode
```

### 설치 확인

Claude Code에서는 `/probe`, Codex에서는 `$mmcode:probe`를 입력합니다. 표식 한 줄이 나오면 설치된 것입니다.

### 새 버전으로 올리기

- Claude Code: GitHub에서 설치했으면 `claude plugin update mmcode@mmcode`를 실행합니다. 로컬 폴더에서 설치했으면 폴더를 바로 읽으므로 `/reload-plugins`면 충분합니다.
- Codex: 설치할 때 플러그인을 `$CODEX_HOME/plugins/cache/` 아래에 복사합니다. 그래서 `codex plugin remove mmcode@mmcode` 뒤에 `codex plugin add mmcode@mmcode`를 다시 실행해야 새 버전이 반영됩니다. GitHub 주소로 등록한 마켓이면 그 앞에 `codex plugin marketplace upgrade mmcode`로 스냅샷을 먼저 갱신합니다.

로컬 사본으로 쓰려면 저장소를 받은 뒤 위 명령의 주소 자리에 그 폴더 경로를 넣습니다.

### 부르는 법 한눈에

| | Claude Code | Codex |
|---|---|---|
| 입구 | `/go` 또는 `/mmcode:go` | `$mmcode:go` |
| 개별 스킬 | `/explain`, `/relay`, `/pair`, … | `$mmcode:explain`, `$mmcode:relay`, `$mmcode:pair`, … |
| `plan` | `/mmcode:plan` (`/plan`은 Claude Code 내장 명령과 겹칩니다) | `$mmcode:plan` |

## 단계별 사용법

처음에는 1단계와 2단계만 알면 됩니다. 일이 커질수록 다음 단계를 하나씩 더 쓰면 됩니다.

### 1단계. 설치가 됐는지 확인하기

프로젝트 폴더에서 Claude Code를 켜고 `/probe`를 입력합니다. 표식 한 줄이 나오면 됩니다. 아무것도 안 나오면 설치 절의 명령을 다시 실행하고 `/reload-plugins`를 입력합니다.

### 2단계. 보통 작업은 `/go` 하나로

`/go` 뒤에 하고 싶은 일을 적습니다. 영어로 바꿀 필요가 없습니다.

```text
/go 목록에서 날짜를 바꿔도 결과가 그대로야. 날짜대로 나오게 고쳐 줘.
```

그러면 이런 순서로 진행됩니다.

1. **경로 한 줄.** `▶ 경로: 버그 수정`처럼 어떤 종류의 일로 보는지 먼저 말합니다. 버그 수정, 기능, 리팩터, 조사, 성능 문제 같은 경로가 있습니다.
2. **작업 이해 화면.** 코드를 고치기 전에 아래와 같은 화면을 보여 줍니다. 틀린 데가 있으면 이때 바로 말하면 됩니다.

   ```text
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    작업 이해 │ 목록 날짜 필터 버그
    난이도 ★★☆☆☆ · 수정 파일 1개
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    📋 이해한 내용
       ▸ 날짜를 바꿔도 목록이 그대로임
       ▸ 날짜에 맞는 목록이 나오게 고침
       ▸ 가정: 검색 버튼 자체는 정상

    🎯 작업 방법
       ▸ 조회 요청에 빠진 날짜 값을 넣음
       ▸ 날짜 3가지로 목록·전체 건수를 확인
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   ```

   - `난이도`는 별 다섯 개 중 칠한 개수입니다. ★1은 문구 수정, ★3은 원인을 찾아야 하는 버그, ★5는 여러 서비스가 얽힌 변경입니다.
   - `가정:`으로 시작하는 줄은 Claude가 확실하지 않아 그렇게 두고 진행하는 내용입니다. 아니면 고쳐 주세요.
   - ★1~2짜리 작은 수정은 이 화면 대신 두 줄로 줄여서 보여 줍니다.
   - 화면만 보고 멈추게 하려면 요청에 "계획만" 또는 "아직 수정하지 마"를 붙입니다.

3. **진행 알림.** 작업 중에는 `⏳ 진행`, `💡 발견`, `❌ 실패`, `❓ 확인 필요` 같은 한 줄 알림만 옵니다. `❓`가 오면 답을 기다리는 중입니다.
4. **작업 완료 화면.** 바뀐 점, 시험 결과, 실제 확인, 남은 일을 한 화면으로 보고합니다. 돌리지 않은 검사는 `미실행`, 확인하지 못한 것은 `미확인`이라고 솔직하게 적습니다.
5. **커밋 확인.** 커밋과 푸시는 혼자 하지 않습니다. "커밋할까요?"라고 물으면 그때 답하면 됩니다.

### 3단계. 고치기 전에 이해부터 확인하고 싶을 때 — `/explain`

`/go`를 거치지 않고 "작업 이해" 화면만 먼저 보고 싶으면 `/explain`을 씁니다.

```text
/explain 결제 완료 메일이 두 번 가는 문제를 고치고 싶어.
```

화면을 보여 준 뒤 바로 작업을 이어 갑니다. 승인을 받고 싶으면 "승인 후 진행"이라고 덧붙이세요. 그러면 화면만 보여 주고 멈춥니다.

### 4단계. 여러 파일에 걸친 큰 작업 — `/mmcode:plan`

기능 추가처럼 파일이 여럿이고 단계가 있는 일은 `/mmcode:plan`을 씁니다. (`/plan`은 Claude Code 내장 명령과 겹치므로 `mmcode:`를 꼭 붙입니다.)

```text
/mmcode:plan 업로드가 끊기면 처음부터 다시 올려야 해. 끊긴 조각부터 이어 올리게 바꿔 줘.
```

달라지는 점은 이렇습니다.

- **계획자와 일꾼.** Claude 본인이 계획자가 되어 일을 나누고, 구현은 일꾼(하위 에이전트)에게 맡깁니다. 간단한 일은 계획자가 직접 합니다.
- **작업 계획 화면.** 작업 이해 화면에 `역할` 구역(누가 무엇을 맡는지, 어떤 등급의 모델을 쓰는지)과 `검증` 구역(시험 몇 건, 교차 검토 여부)이 더해집니다.
- **시험을 먼저 정합니다.** 요구사항마다 시험을 1개 이상 두고, 실제로 들어올 수 있고 틀리면 피해가 있는 경계값만 고릅니다. 버그 수정은 고치기 전에 시험이 실패하는지부터 봅니다.
- **교차 검토.** 데이터 구조나 인증처럼 되돌리기 어려운 변경이면 다른 AI(codex·agy)에게 한 번 더 검토를 맡깁니다. 검토는 기본 2회차까지입니다. 그 뒤에도 지적이 남으면 반영할지, 기록만 할지, 멈출지 사용자에게 묻습니다.
- **일꾼의 보고를 그대로 믿지 않습니다.** diff와 시험 결과로 확인한 뒤에만 승인합니다.

### 5단계. 세션 하나로 끝나지 않는 긴 작업 — `/relay`

며칠 걸리는 일, 모듈 여러 개를 바꾸는 일은 `/relay`로 단위를 나눠 진행합니다. 진행 상황을 인계 문서에 적어 두므로 세션이 바뀌어도 이어 갑니다.

1. `/relay 이 작업을 단위 계획으로 만들어 줘. <작업 설명>`이라고 말합니다. 단위 표와 인계 문서가 `docs/relay/<계획 이름>/`에 생깁니다.
2. "다음 단위 진행해"라고 말합니다. 단위 하나를 작업하고 검수한 뒤 "커밋할까요?"라고 묻습니다.
3. 대화가 길어지면 "세션 바꿔서 이어 가"라고 말합니다. 새 세션에서는 "인계 재개 `docs/relay/<계획 이름>/HANDOFF.md`"라고 하면 상태표가 뜨고 그다음 단위부터 이어 갑니다.
4. 다 끝나면 "close 해줘"라고 말합니다. 임시 권한과 브랜치를 정리하고 종료 체크리스트를 보여 줍니다.

자리를 비우는 동안 혼자 돌게 하는 `auto` 모드도 있습니다. 완료 조건을 명령(예: 테스트 명령)으로 줄 수 있을 때만 씁니다. 자세한 사용법은 [relay 사용법](plugins/mmcode/skills/relay/README.md)에 있습니다.

### 6단계. 다른 AI에게 코딩을 맡기기 — `pair`

"codex한테 시켜" 또는 "agy로 구현해"라고 말하면 이 세션은 계획·브리프·검증만 맡고 코딩은 상대가 합니다.

- herdr 터미널 탭 안이면 같은 탭에 codex 창을 띄워 맡깁니다.
- herdr 밖이면 `agy` 명령을 불러 맡깁니다. `agy`가 없으면 그 사실만 알리고 멈춥니다. 다른 상대로 몰래 바꾸지 않습니다.
- 상대가 "다 했다"고 해도 diff와 시험으로 확인한 뒤에만 승인합니다. 커밋은 여전히 사용자에게 묻습니다.

### 7단계. 확인 도구 세 가지

코드를 바꾸지 않고 확인만 하고 싶을 때 씁니다.

| 이렇게 물으면 | 하는 일 |
|---|---|
| "이 변경이 뭘 깨뜨릴 수 있어?" | `check-impact`. 변경이 안전한 이유가 되는 사실 하나를 찾아, 말이 아니라 실제 코드 실행으로 증명합니다. 증명하지 못하면 `증명 안 됨`이라고 적습니다. |
| "진짜 빨라진 거 맞아?" | `check-benchmark`. 병목, 튜닝, 재현성, 오류 수, 실제로 일이 일어났는지 등 7가지를 실행 증거로 점검한 뒤 판정부터 말합니다. |
| "검증 스킬 만들어 줘" | `make-verifier`. 앱을 사용자처럼 돌려 증거를 남기는 스킬(`verify-<app>`)이나, 동시성·상태 기계의 성질 하나를 증명하는 스킬(`prove-<area>`)을 프로젝트 안에 만듭니다. |

## 자주 묻는 질문

**커밋이나 푸시를 혼자 하나요?**

아닙니다. 끝나면 "커밋할까요?"라고 묻고, 답을 들은 뒤에만 합니다. 푸시도 같습니다.

**영어로 써야 하나요?**

아닙니다. 요청도 화면도 한국어입니다. 코드 식별자와 명령만 원문 그대로 둡니다.

**`/plan`이 안 먹어요.**

`/plan`은 Claude Code 내장 명령입니다. `/mmcode:plan`이라고 적으세요.

**herdr가 뭔가요? 없어도 되나요?**

터미널 탭을 여러 개 띄워 에이전트를 함께 돌리는 도구입니다. 없어도 됩니다. `pair`는 agy 경로를 쓰고, `relay`는 인계 문서를 쓴 뒤 새 세션을 어떻게 시작하는지 안내합니다.

**비용이 많이 들지 않나요?**

계획자는 상위 모델, 일꾼은 하위 모델을 씁니다. 작은 일은 화면도 두 줄로 줄입니다. 검토 회차와 시험 범위에도 상한이 있어서 끝없이 반복하지 않습니다.

**규칙이 너무 많아 보여요.**

사용자가 외울 규칙은 없습니다. `/go` 뒤에 할 일을 적으면 나머지는 Claude가 따릅니다. 규칙 문서는 Claude가 읽는 것이고, 수치·형식 규칙은 이유를 적으면 벗어날 수 있는 기본값입니다.

## 기여자와 개발자를 위한 전제

- 스킬은 커밋·푸시·승인 경계·모델 등급 같은 전역 규칙을 다시 정하지 않습니다. 프로젝트의 CLAUDE.md·AGENTS.md가 항상 우선합니다.
- 스킬이 "전역 규칙을 따른다"고 하는 자리는 다음 네 가지가 있다고 전제합니다. 커밋·푸시는 사용자 확인 뒤에만 합니다. 하위 에이전트에 맡긴 결과는 diff와 시험으로 확인합니다. 공유 워킹트리에서 `stash`·`reset --hard`·`checkout --` 같은 파괴적 git 명령을 쓰지 않습니다. 교차 검토용 외부 에이전트(codex·agy)의 호출법과 한도 확인 방법이 정해져 있습니다. 전역 규칙이 없으면 그 자리에서 보수적으로 행동합니다. 확인하고 진행하고, 교차 검토는 `미실행 · 전역 규칙 없음`으로 적습니다.
- `pair`의 codex 경로와 `relay`의 세션 교체는 herdr 터미널 탭(`HERDR_ENV=1`) 안에서만 동작합니다. herdr 밖에서 `pair`는 agy 경로를 쓰고, `relay`는 인계 문서를 쓴 뒤 새 세션 시작을 안내합니다.
- 스킬 본문은 한국어입니다. 작업 이해·작업 계획·작업 완료 화면은 터미널 폭 50칸 기준으로 그립니다.
- 규칙은 두 층입니다(plan 0절). 전역 규칙·증거 보고·완료 보고 확인은 불변이고, 그 밖의 수치·형식·절차는 기본값이라 이유를 적고 벗어날 수 있습니다.

### 규칙을 더하기 전에

- 새 규칙이나 수치를 더하기 전에 `go`의 스킬 평가 절차(`plugins/mmcode/skills/go/playbooks/eval.md`)로 플러그인이 있을 때와 없을 때를 같은 과제로 블라인드 비교합니다. 비교 없이 더하지 않습니다. 비교 기록은 `docs/`에 남깁니다.
- 수치가 있는 규칙에는 정한 이유(사건·날짜)를 붙입니다. 그 사건이 지금 모델에서 재현되지 않으면 삭제 후보입니다.
- 저장소 검사는 `scripts/check.sh`, 스크립트 시험은 `scripts/test.sh`입니다.
