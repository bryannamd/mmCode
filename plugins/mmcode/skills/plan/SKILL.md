# plan — 계획과 실행

계획과 실행을 맡는 스킬이다. 작업 이해와 범위 설명은 `explain`이 맡는다. 작업 전 화면과 화면 규칙은 explain을 따른다.

- **계획자**: 계획을 세우고, 일을 나눠 맡기고, 결과를 검증하고 검토한다.
- **일꾼**: 코딩, 단순 반복, 조사를 한다.

## 1. 작업 계획 화면

- 계획자가 직접 처리하면 explain의 작업 이해 화면을 쓴다. 🎯 작업 방법 끝에 `▸ 방침:`, `▸ 시험:` 줄을 더한다. 교차 검토 대상이면 `▸ 교차 검토:` 줄도 더한다. 예: `▸ 교차 검토: codex (DB 구조 변경)`. 예: `▸ 시험: 기능 2 · 경계값 1 · 회귀 1`. 시험이 없으면 `▸ 시험: 없음 · <이유>`로 쓴다. 예: `실제 확인만`, `시험 도구 없음`. 작업 계획 화면에서는 `시험 없음   <이유>`로 쓴다.
- 일꾼을 1명 이상 쓰면 그 화면 대신 **작업 계획 화면** 하나만 보여준다. 제목을 `작업 계획`으로 바꾸고 단계 수를 더한다. 🎯에는 `▸ 방침:`만 더하고, 시험과 교차 검토는 `검증` 구역에 쓴다.

```text
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 작업 계획 │ 업로드 실패 재시도
 난이도 ★★★★☆ · 3단계 · 수정 파일 6개
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 📋 이해한 내용
    ▸ 끊기면 처음부터 다시 올려야 함
    ▸ 끊긴 조각부터 이어 올리게 바꿈

 🎯 작업 방법
    ▸ 조각 업로드에 재시도 3회를 추가
    ▸ 3회 실패하면 다시 시도 버튼 표시
    ▸ 받은 조각 위치를 서버에 저장
    ▸ 방침: 최소 수정 (운영 전이라서)

────────────────────── 역할 ──────────────────────
 계획자      설계·검토 · opus급 xhigh
 일꾼 1      업로드 로직 · sonnet급 low
 일꾼 2      시험 작성 · sonnet급 low

────────────────────── 검증 ──────────────────────
 시험 9건    기능 3 · 경계값 4 · 회귀 2
 교차 검토   codex (서버 저장 구조 변경)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

- 머리 부분 둘째 줄에는 단계 수를 더한다. 단계는 계획자가 정한 작업 순서 묶음이다. 예: 구현, 시험, 검토. 일꾼 수와 같지 않아도 된다.
- 구역 제목 줄은 가운데에 제목을 두고 양쪽을 `─`로 채워 굵은 선과 같은 50칸으로 맞춘다.
- 라벨은 12칸으로 맞춘다. 그래야 값이 같은 열에서 시작한다. 완료 화면도 같다.
- 역할 줄은 맡은 일을 먼저, 모델 등급과 effort를 뒤에 쓴다.
- 일꾼은 `일꾼 1`·`일꾼 2`처럼 번호를 붙이고, 진행 알림에서도 같은 번호를 쓴다.
- 해당 없는 줄은 뺀다. 교차 검토를 하지 않으면 `교차 검토` 줄을 뺀다. 세션을 나눠 진행하면 역할 구역에 `세션 인계   단계마다 새 세션` 줄을 더한다.

## 2. 수정 방침

계획자가 프로젝트 성격과 작업 내용을 보고 정한다. 정한 방침과 그 이유를 🎯 작업 방법 블록에 `▸ 방침:` 줄로 적는다.

**필수: 기존 구조 재사용**

- 항상 지킨다. 새로 만들기 전에 기존 컴포넌트·함수·API·패턴을 먼저 찾아 쓴다.
- 새로 만들어야 하면 그 이유를 한 줄로 남긴다.

**선택: 최소 수정**

- **내용**: 현재 문제의 근본 원인을 해결하는 최소 범위만 고친다. 모든 예외에 대비한 과도한 검증·일반화·안전장치·승인 절차를 넣지 않는다.
- **적용하는 경우** (하나라도 해당):
  - 프로젝트 규칙(CLAUDE.md·AGENTS.md)이 이 방침을 정해 두었다.
  - 운영 전·개발 단계 프로젝트, 내부 관리 도구, 시제품이다.
  - 국소 버그·화면·문구처럼 되돌리기 쉬운 변경이다.
- **적용하지 않는 경우** (하나라도 해당하면 위보다 우선):
  - 운영 중인 데이터의 삭제·이전, 금액, 인증·보안, 외부에 공개된 인터페이스를 바꾼다.
  - 사용자가 꼼꼼한 방어나 검증을 요청했다.
- 최소 수정을 적용하지 않으면 방침을 `일반 수정`으로 적는다. 이때는 바뀌는 범위에서 실제로 생길 수 있는 예외 처리와 검증을 넣는다.
- 판단이 애매하면 적용하지 않는다. 그 판단도 방침 줄 하나에 적는다. 예: `▸ 방침: 일반 수정 (운영 데이터 의심)`
- **적용해도 빼지 않는 것**: 4절의 시험과 검증, 교차 검토 대상 판단, 전역 규칙의 커밋·푸시·배포 확인.

## 3. 일 나누기

- **간단한 작업**(난이도 ★1~2): 계획자가 직접 처리한다. 별도 보고서 파일·계획 파일·작업 분할을 만들지 않는다. 작업 완료 화면은 보여준다.
- **★3 작업**: 계획자가 직접 할지 일꾼에게 맡길지 정하고, 그 이유를 `▸ 방침:` 줄에 적는다.
- **★4~5 작업**: 일꾼 1명 이상에게 맡긴다. 여러 일꾼으로 쪼개는 것은 서로 독립적이고 실제로 이득이 있을 때만 한다. 파일 수만 보고 쪼개지 않는다.
- 위임은 현재 환경과 프로젝트 규칙이 허용할 때만 한다. 에이전트 도구가 없으면 계획자가 직접 한다.
- 메인 세션이 계획자를 맡는다. 메인 세션 모델이 계획자급보다 낮고 작업이 길거나 어렵다면, 시작 전에 그 사실을 알리고 계획자급 모델로 바꾸기를 권한다.

모델은 이름이 아니라 등급으로 고른다. 모델은 계속 새 버전이 나오므로 쓸 수 있는 최신 버전을 쓴다.

| 역할 | 등급 (Claude / Codex) | effort |
|---|---|---|
| 계획자 | opus·fable급 / Codex 상위(astra)급 | 보통 `high`, 어렵거나 위험하면 `xhigh` |
| 일꾼 | sonnet·haiku급 / Codex 하위(sol)급 | `low` |

- 일꾼: 기계적이고 단순한 반복은 haiku급, 일반 구현은 sonnet급을 쓴다.
- 일꾼 작업이라도 저장 트랜잭션·권한·동시성을 건드리거나 150줄을 넘는 변경이면 계획자급(opus급)을 쓴다.
- 수정할 파일이나 원인이 특정되지 않은 채로 구현을 일꾼에게 넘기지 않는다. 계획자가 파일과 원인을 특정해 브리프를 확정한 뒤 구현을 맡긴다. 범위와 산출물을 정한 읽기 전용 조사는 일꾼에게 맡길 수 있다.
- 계획자: 아키텍처·데이터 구조·보안·금액·동시성 작업은 상위 등급과 `xhigh`를 쓴다.
- 위임할 때 model과 effort를 반드시 적는다.
- 일꾼에게 주는 지시에는 목표, 맡을 파일, 건드리면 안 되는 범위, 완료 기준, 통과해야 할 시험을 쓴다. 대화나 코드를 통째로 붙이지 않는다. 코드는 일꾼이 직접 읽는다.
- 계획자는 범위와 설계 판단, 결과 합치기, 최종 검증을 맡는다. 일꾼이 한 조사와 구현을 되풀이하지 않는다.
- 다시 맡길 때 같은 지시·같은 등급·같은 effort를 그대로 반복하지 않는다. 먼저 실패 원인을 가른다. 환경·권한·판정 명령 오류면 재위임하지 않고 환경을 고치거나 중단한다. 일꾼의 diff가 브리프를 다 지켰는데 브리프에 없던 파일·조건·규격 때문에 깨졌으면 브리프 쪽이다. 원인을 좁혀 적어 같은 설정으로 다시 맡긴다. 브리프에 적힌 파일·요구 동작·경계 조건을 빠뜨렸거나 로직을 틀렸으면 역량 쪽이다. 등급을 한 단계 올려 다시 맡긴다(haiku급 → sonnet급 low → 계획자급 low. 이미 계획자급이면 effort를 한 단계). 가르지 못하면 미확인으로 두고 재현과 로그를 먼저 보탠다. 상향은 단위당 1회다.
- 일꾼의 완료 보고를 그대로 믿지 않는다. diff와 시험 결과로 확인한다. 같은 완료 기준으로 다시 맡기는 것은 2회까지다. 그래도 안 되면 계획자가 직접 하거나 사용자에게 알린다.

## 4. 시험과 검증 (깐깐하게)

구현 전에 통과·실패를 판정할 수 있는 완료 기준과 시험 계획을 세운다. 여기서 시험은 자동으로 돌리는 테스트만 뜻한다. 브라우저나 실제 데이터로 보는 것은 `실제 확인`이라 부르고 시험 건수에 넣지 않는다. 작업 계획 화면의 `시험` 줄(직접 처리할 때는 `▸ 시험:` 줄)에 종류별 건수로 적는다.

- **기능**: 요구사항마다 시험을 1개 이상 둔다. 위험이 낮은 문구·스타일 수정은 시험을 만들지 않고 실제 확인만 한다.
- **시험 도구가 없을 때**: 프로젝트에 자동 시험 도구가 없으면 새로 들이지 않는다. `▸ 시험: 없음 · 시험 도구 없음`으로 적고 실제 확인으로 대신한다. 도구를 들일지는 사용자가 정한다.
- **경계값과 예외**: 이번 변경에 실제로 들어올 수 있는 것은 빠짐없이 고른다. 예: 빈 값, 최대·최소, 잘못된 입력, 권한 없음, 결과 0건.
- **회귀**: 바꾸지 않은 핵심 동작이 그대로인지 확인한다.
- **실패 먼저 확인**: 버그 수정이면 고치기 전에 시험이 실패하는지 먼저 본다.
- **실제 확인**: 화면 변경은 프로젝트가 정한 브라우저에서 확인한다. 조회·필터 변경은 목록·전체 건수·페이지 조건이 서로 맞는지 확인한다. 데이터 규격 변경은 보내는 쪽과 받는 쪽, 기존 데이터 전환을 모두 확인한다.
- 기대값은 구현이 아니라 요구사항에서 정한다. 구현을 그대로 베낀 시험은 만들지 않는다.
- 프로젝트 필수 검사는 한다. 이미 통과한 검사는 그 뒤에 코드가 바뀌지 않았으면 다시 돌리지 않는다.
- 코드 검토, 정적 검사, 시험, 실제 확인, 배포 완료는 각각 따로 적는다. 한 가지 결과를 다른 것의 통과로 쓰지 않는다. 명령과 결과를 남긴다. 실행하지 않은 검사를 통과라고 쓰지 않는다.
- 환경이나 권한 때문에 못 한 항목은 이유와 남은 일을 알리고, 할 수 있는 일은 끝낸다.

## 5. 교차 검토 (다른 AI)

- **언제**: 되돌리기 어렵거나 영향이 넓은 변경이다. 데이터 구조, 외부에 공개된 인터페이스, 인증·보안, 금액, DB 변경·삭제가 여기에 해당한다. 사용자가 요청하면 이 경우가 아니어도 한다.
- **누가**: 코드를 쓰지 않은 에이전트가 한다. 가능하면 다른 종류의 AI를 쓴다. 예: Claude가 썼으면 codex나 agy. 쓸 수 없으면 새로 띄운 Claude 에이전트가 한다.
- 작성자의 대화는 넘기지 않는다. 파일 경로와 판정 기준만 준다.
- 호출 방법과 사용 한도 확인은 전역 규칙(CLAUDE.md·AGENTS.md)을 따른다.
- 지적은 해당 코드를 직접 열어 확인한 뒤 반영한다. 확인하지 못한 지적은 `미확인`으로 쓴다.
- 수정 방침과 맞지 않는 지적은 반영하지 않는다. 그 이유를 한 줄 남긴다.
- 지적을 반영했으면 같은 검토자에게 바뀐 부분만 다시 보낸다. 반영할 지적이 0건이 될 때까지 반복한다. 반영할 지적이 0건이고 `미확인` 지적도 없을 때만 `통과`라고 쓴다. 이유를 남기고 반영하지 않은 지적은 세지 않는다. 다시 검토하지 못했으면 `지적 2건 반영 · 재검토 미실행`처럼 쓴다.
- 대상인데 못 했으면 완료 화면에 `교차 검토   미실행 · <이유>`를 남긴다. 검토했다고 쓰지 않는다.

## 6. 전문가 기준 반복 검토

목표: 그 분야 전문가가 봐도 고칠 곳이 없는 결과.

- 계획자는 작업 분야 최고 전문가의 기준으로 결과를 다시 본다. 코드는 숙련된 프로그래머, 화면은 UI/UX 전문가, 문서는 편집자의 눈으로 본다.
- 전역·프로젝트 규칙이 별도 검수 에이전트를 요구하면 그 규칙을 따른다. 그 결과는 반복 검토 회차로 센다. 5절 교차 검토와는 따로다.
- 검토하고, 고치고, 다시 검사하는 과정을 반복한다. 한 회차 검토에서 지적이 0건이면 멈춘다. 수정 방침과 맞지 않아 이유를 남기고 반영하지 않은 지적은 세지 않는다.
- 같은 문제가 두 회차 연속 나오면 고치는 방식을 바꾼다. 방식을 바꾼 다음 회차에도 남으면 그 문제는 `남은 일`에 적고, 이후 회차의 지적 수에서 뺀다.
- 검토에는 필요한 만큼 토큰을 쓴다. 비용은 길거나 어려운 작업에서 반복 작업을 일꾼에게 맡기고 세션을 나눠서 줄인다. 검토를 줄여서 아끼지 않는다.
- 반복은 요청 범위 안에서만 한다. 기능을 더하거나 범위를 넓히지 않는다. 정한 수정 방침이 우선한다. 예: 최소 수정 방침이면, 실제로 들어오지 않는 입력에 대비한 방어 코드는 검토에서 권해도 넣지 않는다. 시험에서 실패한 경계값은 고친다.
- 회차마다 무엇을 고쳤는지 진행 알림 한 줄로 남긴다.

## 7. 세션 인계와 비용

- 작업이 여러 단계로 길어지거나 대화가 커지면, `relay` 스킬이 있는 경우 그 스킬로 새 세션에 넘긴다. 짧은 작업에는 쓰지 않는다.
- 별도 문서는 사용자가 요청하거나 작업을 이어가는 데 꼭 필요할 때만 쓴다.

## 8. 진행 알림

진행 중에는 아래 8가지만 알린다. 코드 블록 없이 일반 텍스트 한 줄로 쓰고, 줄 맨 앞 기호와 이름으로 종류를 구분한다.

- `⏳ 진행 │ 3단계 중 2단계 끝 ▰▰▰▰▰▰▰▱▱▱ · 마지막 단계 시작`
- `💡 발견 │ 서버 조회에도 날짜 값이 빠짐 · 이번에는 안 고침`
- `📐 범위 변경 │ 수정 파일 6개에서 8개로 · 공통 함수도 고침`
- `🔧 반복 검토 │ 2회차 · 버튼 문구 통일, 빈 목록 안내 추가`
- `❌ 실패 │ 경계값 시험 2건 · 일꾼 1에게 다시 맡김 (1/2회)`
- `🔍 교차 검토 │ codex 지적 2건 · 2건 반영, 재검토 요청`
- `🔁 세션 인계 │ 2단계 끝 · 새 세션으로 넘김`
- `❓ 확인 필요 │ DB 쓰기 승인 필요 · 답을 기다림`

- 진행 막대는 단계가 3개 이상일 때만 넣는다. 10칸이고, 끝난 단계 비율만큼 `▰`를 채운다(반올림). 앞 문구도 끝난 단계 수로 쓴다.
- 한 줄은 60칸 안에 쓴다. 이모지는 줄 맨 앞에 하나만 쓴다.
- `❓`는 사용자 입력 없이는 진행할 수 없을 때만 쓴다. 무엇이 필요한지 같은 줄에 쓴다.
- `💡`에는 새로 알게 된 문제를 이번에 고치는지 같은 줄에 쓴다. 고치려면 아래 `📐` 기준을 따른다.
- `📐`는 같은 목표 안에서 고칠 위치만 늘 때 쓰고, 알린 뒤 그대로 진행한다. 목표나 기능이 늘면 `❓`로 먼저 묻는다.

## 9. 완료 보고

작업을 마치면 작업 완료 화면으로 보고한다.

```text
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 작업 완료 │ 업로드 실패 재시도
 시험 9/9 통과 · 남은 일 2건
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 바뀐 점     자동 재시도 3회 추가
 검사 결과   시험 9/9 · 빌드 통과
 실제 확인   브라우저에서 끊김 복구 확인
 교차 검토   codex 지적 2건 반영 후 통과
 다시 고침   경계값 처리 · 문구 등 5건
 남은 일     배포 필요 · 커밋 확인 대기
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

- 머리 부분 둘째 줄은 `시험 <통과 수>/<전체 수> 통과 · 남은 일 N건`으로 쓴다. 실패가 있으면 `시험 7/9 통과 · 실패 2건 · 남은 일 3건`처럼 실패 수를 더한다. 시험이 없으면 `시험 없음 · 남은 일 N건`으로 쓴다.
- 줄 순서는 바뀐 점, 검사 결과, 실제 확인, 교차 검토, 다시 고침, 남은 일이다. 라벨을 새로 만들지 않는다. 값은 한 줄에 공백 포함 한글 18자 안팎으로 쓰고, 길면 다음 줄에 같은 열로 이어 쓴다.
- 브라우저·실제 데이터로 확인할 대상이 없는 작업이면 `실제 확인` 줄을 뺀다. 대상이 있는데 못 했으면 `미실행 · <이유>`로 남긴다.
- `검사 결과`에는 시험·정적 검사·빌드를 적는다. 배포 여부는 `남은 일`에 적는다.
- `다시 고침`에는 시험 실패나 검토 지적 때문에 다시 고친 것을 적는다. 반복 검토로 고친 것도 여기에 넣는다. 고친 내용을 먼저 쓰고 건수를 뒤에 쓴다.
- 숫자는 실제로 실행한 결과만 쓴다. 하지 않은 검사는 `미실행 · <이유>`, 사실을 확인하지 못한 것은 `미확인`으로 쓴다.
- 실패가 남아 있으면 숨기지 않는다.
- 다시 고친 일이 없으면 `다시 고침` 줄을 뺀다. 교차 검토 대상이 아니면 그 줄을 뺀다.
- 남은 일이 없으면 `없음`으로 쓴다. 머리 부분도 `남은 일 없음`으로 쓴다.
