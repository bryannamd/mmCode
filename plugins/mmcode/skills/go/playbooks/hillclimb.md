# 지표 개선 반복
언제: 지표 하나를 목표까지 가설·측정으로 반복해 올릴 때. 한 번 고치는 일은 `perf-issue.md`나 `bug-fix.md`를 쓴다.
## 단계
1. 지표 1개, 좋아지는 방향, 목표, 시도 횟수 하한을 정한다. 예: "기준선보다 50% 좋아지고 시도 10회 이상".
   - 하한은 운 좋은 첫 성공으로 끝나는 것을 막는다.
   - 사용자가 준 숫자를 우선한다. 목표가 없으면 묻는다. 하한만 없으면 10회로 정해 알리고 진행한다.
2. 사용자 불만을 재현하는 사례를 고른다(데이터 크기·이력·상태·동시성). 재현이 안 되면 반복을 멈추고 재현부터 고친다.
3. 측정 도구를 만들고 변화를 잡아내는지 증명한다.
   - 성격이 다른 현실적 사례를 여러 개 돌린다. 목표 사례는 증상을 재현해야 한다. 쉬운 사례와는 예상한 만큼 차이가 나야 한다.
   - 구분이 안 되면 사례나 지표를 바꾼다.
4. `check-benchmark` 스킬로 측정 도구를 점검한 뒤 동결한다.
   - 동결 뒤에는 명령 하나가 지표를 낸다.
   - 출력에 오류 수와 처리한 일의 양을 함께 찍는다. 잡음을 넘도록 여러 번 측정해 중앙값을 쓴다.
5. 변경 전에 기준선과 회귀 시험(계속 통과해야 하는 시험)의 통과 상태를 기록한다.
6. 결정 로그 `decision.tsv`를 저장소 밖 scratch 폴더에 만든다. 시도마다 1행이다: id, 가설, 변경, 전, 후, 변화량, 시험, 판정(유지/되돌림), 메모. 시도 전마다 읽는다.
7. 가설마다 구체적인 원리를 댄다. 예: "부팅 경로에서 X를 미룬다. 첫 화면을 막기 때문이다". 성능 지표면 `perf-issue.md` 2단계 순서로 가설을 줄 세운다. 그 단계의 멈춤 규칙은 쓰지 않는다.
8. 가설 하나, 변경 하나로 루프를 돈다. 시도는 하위 에이전트에 맡겨도 된다. 등급은 plan 3절 등급 표를 따르고 diff는 직접 확인한다.
   - 동결한 도구로 전후를 측정하고 회귀 시험을 돌린다.
   - 지표가 잡음 밖으로 움직이고 시험이 통과할 때만 유지한다. 아니면 변경을 전부 되돌린다.
   - 시도마다 `decision.tsv`에 1행을 쓴다. 유지와 되돌림 모두 쓴다.
   - 이득 1건마다 "커밋할까요?"라고 묻는다. 커밋하기로 하면 `git add <바꾼 파일>`만 쓰고 `git add -A`는 쓰지 않는다.
9. 연속으로 되돌렸으면 방향을 바꾼다. 다른 종류를 시도하거나, 거의 효과가 났던 시도를 합치거나, 소스를 다시 읽는다. 정확성과 단순함이 숫자보다 앞선다. 동작을 깨는 이득은 되돌린다.
10. 목표와 하한을 채우면 멈춘다. 남은 아이디어가 비용보다 이득이 작아도 멈춘다. 싸게 해 볼 가설이 남았으면 멈추지 않는다. 목표를 낮춰서 맞추지 않는다. 막혔으면 돌지 말고 사용자에게 알린다.
