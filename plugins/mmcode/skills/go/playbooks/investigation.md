# 조사
언제: 어떻게 동작하는지, 왜 이렇게 만들었는지, 확실한지 알아볼 때. 읽기만 한다.
## 단계
1. 읽기만 한다. 코드·설정·데이터를 바꾸지 않는다.
   - 변경이 필요해지면 멈추고 사용자에게 알린다.
   - 그 뒤 맞는 경로(`버그 수정`·`기능`·`리팩터`·`성능 문제`)로 새로 시작한다.
2. 질문을 한 문장으로 적는다. 사용자가 질문에 넣은 추측("성능 때문이겠지")은 후보 하나로만 다룬다. 증거로 따로 확인한다.
3. 코드를 따라 읽는다. "왜"를 묻는 질문이면 이력도 찾는다(git log·blame·PR·이슈·문서). 코드만으로는 만든 이유를 알 수 없다.
4. 주장마다 확신도를 하나 붙인다. 코드가 하는 일로 작성자의 의도를 짐작하면 추정이다.
   | 확신도 | 뜻 | 쓰는 말 |
   |---|---|---|
   | 직접 확인 | 작성자가 쓴 글(PR 설명·주석·문서)이나 실행 결과가 답을 말한다 | 단정 + 출처 |
   | 근거 있음 | 간접 증거 여러 개가 같은 결론을 가리킨다 | 단정 + 증거를 하나씩 인용 |
   | 추정 | 맥락에서 읽어 낸 해석이다. 직접 뒷받침하는 증거는 없다 | "~로 보인다" + 추론 과정 |
   | 짐작 | 얇은 증거에 다른 설명도 똑같이 맞는다 | "~일 수 있다" + 짐작이라고 밝힘 |
   | 모름 | 찾아봤지만 못 찾았다 | 찾은 곳과 검색어를 적음. 없다고 단정하지 않음 |
5. 증거가 서로 부딪히면 둘 다 출처와 함께 적는다. 이야기가 깔끔해지는 쪽만 고르지 않는다.
6. 대안 중에서 고르는 질문이면 장단점 표와 추천을 쓴다.
7. 끝내기 전에 주장마다 출처를 확인한다. 출처가 없으면 추정으로 내린다. 모름이 하나도 없으면 빠뜨린 것이 없는지 다시 본다.
## 보고
결론 1~2줄 → 근거(file:line) → 확신도 → 다음 할 일 하나 순서로 쓴다.
"확실한가?"에는 실제 판단과 이유를 쓴다. 전제가 틀렸으면 틀렸다고 말한다.
