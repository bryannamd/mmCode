# 버그 수정
언제: 보고된 결함을 고칠 때. 재현 → 원인 → 실패 시험 → 수정 순서다.
## 단계
1. 버그가 여러 건이면 먼저 가른다. 건마다 빈도(얼마나 자주 나나)와 심각도(나면 무엇이 깨지고 복구에 얼마나 드나)를 1~10으로 매기고 근거를 한 줄 적는다.
   - 곱이 문턱 미만이면 코드를 건드리지 않고 완료 화면 `남은 일`(relay면 `DEBT.md`)에 적는다. 문턱은 사용자가 준 값을 쓰고, 없으면 5다(2026-11-17 사용자 제시값).
   - 데이터 손실·보안·금액은 점수와 무관하게 고친다. 사용자가 한 건을 지목해 고치라고 했으면 가르지 않는다.
   - 이슈 등록은 외부 전송이다. 사용자가 요청할 때만 한다.
2. 고칠 건을 직접 재현한다. 재현하기 전에는 원인을 추측하지 않는다.
   - 재현이 안 되면 조건을 좁히거나 로그를 넣어 다시 시도한다.
   - 사용자에게 재현을 부탁하는 것은 도구로 닿지 않는 이유를 구체적으로 댈 수 있을 때만 한다.
3. 원인을 못 찾으면 이분 탐색한다. `git bisect`나 코드 범위 반분으로 범위를 절반씩 줄인다.
   - 단계마다 실행 결과로 한쪽을 지운다.
   - 남은 원인이 어떻게 일어나는지 실행 증거로 확인한 뒤에 고친다.
4. explain 화면을 띄운다. 작업 방법 블록 끝에 `▸ 경로: 버그 수정` 줄을 더한다. plan의 `▸ 방침:` 줄이 있으면 그 앞에 둔다.
5. plan 절차를 따른다.
   - 4절 "실패 먼저 확인"에 따라 고치기 전에 시험이 실패하는지 본다.
   - 시험으로 잡기 어려우면 2단계의 재현 절차가 실패 증거다.
   - 증거가 뒷받침하는 가장 작은 수정만 넣는다. "혹시 도움될" 방어 코드는 넣지 않는다.
   - 고친 뒤 같은 방법으로 다시 재현해 통과를 확인한다.
