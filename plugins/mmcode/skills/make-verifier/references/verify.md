
# 동작 모드 — 앱을 사용자처럼 돌려 증명하는 스킬(`verify-<app>`) 만들기

진지한 프로젝트라면 실제 앱을 조작해 동작을 증명하는 스크립트화된 방법이 필요하다. 앱을 띄우고, 사용자처럼 기능을 써 보고, 증거를 남기는 방법이다. 이 스킬은 그것을 저장소에 맞춘 프로젝트 전용 스킬(`.agents/skills/verify-<app>/`)로 만든다. 결과물은 사람이 아니라 다음 에이전트를 위해 쓴다. 그 에이전트는 앱을 본 적 없이, 작업 도중에, 아무 맥락 없이 이 스킬을 읽는다.

## 1. 사용자가 아니라 저장소에 묻는다

아래 항목은 코드베이스에서 답을 찾는다. 관찰할 수 없는 것만 사용자에게 묻는다.

- **접점:** 사용자가 실제로 만지는 것은 무엇인가? 웹 UI, CLI/TUI, 데스크톱 앱, API, 모바일 앱, 라이브러리? 저장소에 접점이 여럿일 수 있다. 주된 것 하나를 고르고 나머지는 적어 둔다.
- **기동:** 앱을 로컬에서 어떻게 띄우나? 저장소가 문서화한 개발 명령(패키지 스크립트, Makefile, README 빠른 시작)을 우선한다. 포트, 환경 변수, 시드 데이터, 인증을 적어 둔다.
- **조작:** 에이전트가 프로그램으로 앱과 어떻게 상호작용할 수 있나? 기존 자동화 도구를 먼저 본다: Playwright/Cypress 스펙, expect 스크립트, PTY 보조 도구, curl로 호출할 수 있는 엔드포인트, 디버그 포트. 그다음에야 일반 방법을 고른다: 웹과 Electron은 브라우저/CDP, CLI/TUI는 tmux/PTY 기반 조작 도구, 서비스는 일반 HTTP.
- **관찰:** 어떤 증거를 남길 수 있나? 스크린샷, 터미널 기록, 응답 본문, 로그, 종료 코드, DB 상태.
- **격리:** 인스턴스 둘이 나란히 돌 수 있나(포트, 데이터 폴더, 프로필)? 안 되면 생성하는 스킬에 그렇게 적는다. 공유 인스턴스를 둘이 동시에 조작하기를 거부하는 편이 사용자 세션을 망가뜨리는 것보다 낫다.

체크아웃한 코드가 그대로 빌드·기동되지 않으면, 생성하기 전에 먼저 고치거나 정확히 보고한다. 깨진 기반 위에 쓴 스킬은 틀린 단계를 가르친다. 관련 없는 자산이 없어서 기동이 막히면(API가 서빙하지 않는 정적 폴더, 샘플 설정 파일) 생성하는 스킬이 그 자산을 만들 수 있다. 검증용 임시 구조물임을 분명히 표시하고, 정리할 때 지운다.

## 2. 스킬을 생성한다

위치·링크·frontmatter는 SKILL.md 2절 공통 규칙대로 한다(`name: verify-<app>`, `description`에 앱 이름·접점·언제 쓰는지). 아래 섹션을 모두 넣고, 각 섹션을 조사에서 실제로 찾은 내용으로 채운다(빈칸을 남기지 않는다).

- **기동(Launch):** 검증용으로 앱을 띄우는 정확한 명령과, 준비됐음을 아는 방법(로그 한 줄, 프롬프트). 빈 데이터 폴더에서 시작해 마이그레이션과 시드 데이터까지 거쳐 쓸 수 있는 상태에 이르러야 한다. 준비됨은 '쓸 수 있음'이다. 프로세스가 응답한다는 뜻이 아니다. 데이터베이스 상태 검사는 초기화 스크립트가 아직 도는 중에도 통과할 수 있다. 종료 방법도 넣는다. 수명이 짧은 CLI나 TUI는 계속 띄워 둘 서버가 없다. 이 경우 기동은 바이너리를 한 번 빌드하거나(또는 의존성을 설치하고), 조작할 때마다 격리된 PTY나 tmux 세션에서 시작한다는 뜻이다.
- **진단(Doctor):** "이 인스턴스를 조작할 가치가 있나?"에 답하는 읽기 전용 점검 하나. 프로세스가 떠 있는지, 버전·빌드가 맞는지, 포트를 연 프로세스가 우리가 띄운 것인지, 인증이 유효한지 본다. 뭔가 이상해 보이면 에이전트가 이것을 가장 먼저 돌린다.
- **조작(Drive):** 이 저장소의 실제 선택자·명령으로 쓴 조작 방법. 예시가 아니라 실제 값이다. 좌표나 탭 순서보다 안정적인 식별 수단(ARIA 레이블, data 속성, 프롬프트 문자열, 라우트 경로)을 우선한다. 브라우저 확인은 프로젝트·전역 규칙이 정한 브라우저 도구로 하고, 끝나면 그 도구의 정리 절차를 따른다.
- **증거(Evidence):** 증명을 위해 무엇을 남기고 어디에 두는지. 증명 기준을 적는다. 내부 setter나 테스트 전용 엔드포인트가 아니라 실제 사용자 경로를 거친다. 마지막 화면만이 아니라 동작과 그 결과 상태를 남긴다. 눈에 보이는 것과 함께 부수 효과(써진 파일, 들어간 행, 보낸 메시지)를 확인한다. 모의 객체(mock)는 프로덕션 경계가 이미 외부 시스템을 격리하는 곳에서만 쓴다. 안전한 경로가 dry-run이나 테스트 모드라면, 이름을 믿지 말고 무엇을 실제로 건너뛰는지 관찰해서(파일, 네트워크, git ref) 확인한다. 일부 dry-run은 여전히 네트워크에 접속하거나 브라우저를 연다.
- **정리(Cleanup):** 이번 실행이 만든 인스턴스를 내리는 방법. 이름이나 패턴으로 프로세스를 찾거나 죽이지 않는다(`pkill`·`killall`·`pgrep` 금지). 기동할 때 자기가 시작한 프로세스의 핸들·PID·시작 시각을 기록하고, 그것만 종료한다. 정리는 인스턴스와 임시 상태를 지운다. 증거는 지우지 않는다. 증명 산출물은 정리 뒤에도 스킬이 지정한 위치에 남는다.
- **보조 스크립트(Helpers):** 스킬에 넣는 스크립트는 모두 실행 가능해야 하고, 호출 방법을 스킬 본문에 보인다. 읽는 사람이 거꾸로 분석해야 알 수 있는 보조 스크립트는 보조 스크립트가 아니다.

## 3. 기능 지도를 심는다

`.agents/skills/verify-<app>/features/README.md`와, 찾아낸 사용자 기능마다 파일 하나를 만든다(경로, 명령, 메뉴, 문서에서 우선 3~5개로 시작). 형식은 이 폴더의 [`feature-map-example/`](feature-map-example/)을 따른다: README 색인 하나와 기능별 파일 하나. 각 파일은 사용자 시점에서 답한다: 기능이 무엇인지, 어떻게 도달하는지, 조작 도구로 어떻게 조작하는지, 어떤 관찰 가능한 최종 상태가 동작을 증명하는지. H2 네 개는 `하위 기능`, `도달 방법 (사용자 시점)`, `조작하기 (<도구>)`, `주의할 점`이다. 시드 데이터에 시나리오가 요구하는 전제 조건이 없으면, 시나리오는 실패로 보고하고 이유를 그 기능의 `주의할 점`에 적는다. 통과시키려고 시나리오를 약하게 만들지 않는다. 이 지도는 저장소가 유지하는 검증의 원천이다. 지도에 진입점이 여럿인데 편한 진입점 하나만 조작한 증명은 불완전하다.

## 4. 넘기기 전에 생성한 스킬을 증명한다

스킬의 지시를 처음부터 끝까지 한 번 그대로 실행한다: 기동, 진단, 지도에 있는 기능 하나 조작, 증거 수집, 정리. 기능 하나면 충분하다. 나머지를 다음 실행이 다룰 수 있게 지도가 있다. 정리 뒤에 증거가 지정한 위치에 아직 있는지 확인한다. 증거를 지우는 정리는 이 단계에서 실패다. 실패한 부분을 고친다. 실패한 시도 뒤에도 생성한 정리 절차를 돌려서, 망가진 시도가 프로세스와 포트를 남기지 않게 한다. 실제 대상 대신 대역에서 증명했다면(새 VM 대신 컨테이너, 원격 스택 대신 로컬 스택), 대역이 해 준 설정 단계 중 실제 대상에는 없는 것을 모두 나열한다. 그 단계들은 실제 대상에서 실행해 보기 전까지 미검증으로 남는다.
