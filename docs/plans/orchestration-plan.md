# mmCode 실행 체계 계획

작성일: 2026-11-15 (같은 날 전체 재구성, 교차 검토 1회차 반영)
상태: 설계 확정 대기. 정해야 할 것 4건(12절).
관련 문서:

- 모니터: `docs/plans/monitor-plan.md`
- 증거 설계: `plugins/mmcode/skills/plan/references/DESIGN-evidence.md`
- 제품 기록: `PRODUCT.md`
- 협업 체계 계획(기억, 전역 규칙, 고정 컨텍스트): `tools/obsidian-memory/docs/PLAN_2026-11-15_agent-collab-system.md`
- 교차 검토 결과: `docs/plans/review/CODEX_REVIEW.md`, `docs/plans/review/AGY_REVIEW.md`

## 1. 한 문장

사람은 코드를 읽지 않는다. 완료 기준을 승인하고, 기계가 낸 증거로 완료를 믿고, 기계가 정하지 못하는 것만 결정한다.

목표:

1. mmCode의 구현 능력을 유지한다.
2. 단위가 완료됐다는 판정을 사람의 검토가 아니라 증거로 내린다.
3. 프로젝트 현황을 한 화면에서 보고 클릭으로 개입한다.
4. 세션이 바뀌거나 끊겨도 다시 설명하지 않고 이어 간다.

범위 밖: 터미널 관리(Herdr가 맡는다), 기억과 전역 규칙(협업 체계 계획이 맡는다), 자체 인증, 여러 머신 분산 실행, 상시 역할 팀, 새 모델 선택 시스템.

## 2. 시스템 한 장

모든 단위는 같은 고리를 돈다.

```text
            ┌──────────── 사람 ────────────┐
            │ 계획 승인 · 결정 · 지시       │
            └──────┬───────────────▲───────┘
                   ▼               │ 알림: 내가 나서야 하나
 완료 기준 ─► 실행 ─► 증거 ─► 단계 전환 ─► 기록 ─► 화면 · 인계 문서 · 재개
 (계획 파일) (에이전트) (검사)  (증거 없으면 거부)  (이벤트 파일)
```

규칙은 두 개다.

1. **정의는 계획 파일에, 일어난 일은 기록에 둔다.** 계획 파일은 무엇을 할지 정한다(단위 표, 완료 기준, 위험 등급). 이벤트 파일은 무슨 일이 일어났는지 적는다. 화면, 인계 문서, 진행 표, 재개는 이 둘을 읽은 결과다.
2. **단계는 증거로만 넘어간다.** 단계를 바꾸는 명령은 하나이고, 필요한 증거가 기록에 없으면 거부한다.

부품은 계획 파일을 읽고, 기록을 쓰거나 읽는다. 부품끼리 직접 상태를 주고받지 않는다.

| 부품 | 기록에 쓰는 것 | 읽는 것 | 지금 |
|---|---|---|---|
| 단계 전환 명령 | 단계 전환, 멈춤, 재개, 커밋 | 계획 파일, 증거, 열린 지시 | 신규(U2) |
| 검사 실행(`eval-goal.sh run`, 검수) | 검사 결과 | 계획 파일의 완료 기준 | 일부 있음 |
| 계획자 | 계획 승인 기록, 결정 요청 | 결정 답, 지시 | 규칙 있음, 기록 없음 |
| 모니터 | 지시, 결정 답 | 전부 | 화면 설계 중(별도 세션) |
| 인계 문서 생성 | 없음 | 전부 | 신규(U2) |
| 세션 교체(`rotate.sh`) | 세션 시작·종료 | 없음 | `hc` 전환 끝(U1). 이벤트 쓰기는 U2 |

## 3. 공통 어휘

스킬, 스크립트, 인계 문서, 모니터가 이 절의 낱말과 값을 똑같이 쓴다.

### 3.1 낱말

| 낱말 | 뜻 | 쓰지 않는 말 |
|---|---|---|
| 계획 파일 | `PLAN.md`. 단위 표, 완료 기준, 위험 등급, 완료 조건을 담는다 | |
| 단위 | 계획을 나눈 일 하나. 브리프 1, 검수 1, 커밋 1. ID는 `U<번호>` | 조각, 기능 단위 |
| 완료 기준 | 단위 하나가 끝났는지 판정하는 시나리오 묶음 | |
| 완료 조건 | 계획 전체가 끝났는지 판정하는 명령(auto 모드의 `cmd:`) | |
| 계획자 | 계획, 위임, 통합을 맡는 세션. 전역 규칙의 Advisor | 주 에이전트 |
| 일꾼 | 구현을 맡는 에이전트. 전역 규칙의 Worker | 구현자 |
| 검수자 | 새 맥락에서 변경을 판정하는 에이전트 | |
| 시험 | 시험 코드 | 테스트 |
| 검사 | 완료 기준을 판정하는 실행 하나. 검사 명령 또는 실제 확인 | |
| 검증 | 단계 이름(3.2). 검사를 실행하는 단계 | |
| 검수 | 단계 이름(3.2). 독립 검수와 UI 검수를 하는 단계 | 리뷰 |
| 교차 검토 | 다른 회사 모델(codex, agy)에게 맡기는 검수 | 교차 검증 |
| 변형 점검 | 검수자가 결함 하나를 넣어 시험이 실패하는지 보는 확인 | 뮤테이션 |
| 회차 | 검수나 검토를 한 번 도는 것 | 라운드 |
| 기록 | 이벤트 파일 `events.jsonl` | |
| 세션 대화 파일 | Claude Code가 남기는 `<세션>.jsonl` | 세션 기록 |
| 인계 문서 | `HANDOFF.md` | 핸드오프 문서 |
| 터미널 | `hc`가 실행하는 터미널 하나. 주소는 `t3d` 형식 | pane, 패널 |
| 지시 | 사용자가 실행에 주는 명령. 종류는 3.3절 | 개입(화면 설명에만 쓴다) |
| 결정 요청, 결정 답 | 계획자가 묻고 사용자가 답하는 것 | |
| 사전 결정 | 계획을 승인할 때 미리 받은 결정 답. 계획 파일의 "사전 결정" 절에 적는다(7.1절) | 선결정 |
| 결정 대기열 | 아직 답이 없는 결정 요청의 목록 | 결정 대기 목록 |
| 멈춤 | 단위나 계획이 진행하지 않는 상태 | |

### 3.2 단계

| 단계 | 기계 값 | 모니터의 장소 | 이 단계에 들어오는 조건(기록에 있어야 하는 것) |
|---|---|---|---|
| 대기 | `queued` | 왼쪽 선반 | 계획 승인 기록에 단위가 있다 |
| 구현 | `build` | 책상 | 선행 단위가 완료. 열린 정지 지시가 없다 |
| 검증 | `verify` | 시험대 | 변경이 단위의 경로 범위 안. 등급이 요구하면 "실패 먼저" 증거 |
| 검수 | `review` | 벽 화면 | 완료 기준의 검사가 모두 통과 |
| 완료 | `done` | 오른쪽 선반 | 등급이 요구하는 검수 증거(3.4)가 통과. 커밋 기록 또는 `없음(변경 없음)` 기록 |

- 검증이나 검수에서 실패하면 구현으로 되돌아간다. 사유를 기록한다.
- 가벼움 등급은 독립 검수를 요구하지 않는다. 화면 변경이 없으면 검수 단계를 바로 지난다. 화면 변경이 있으면 UI 검수를 통과해야 완료된다.
- 인계 문서 상태표의 `미착수`는 대기, `진행`은 구현·검증·검수, `완료`는 완료에 해당한다. `보류`와 `blocked`는 단계가 아니라 멈춤이다(3.3).
- `eval-goal.sh`의 `stage` 값(`started`, `reviewed`, `committed`, `merged`, `cleaned`)은 git 작업의 내부 순서다. 이름과 값을 바꾸지 않는다. 사용자에게 보이는 단계의 필드 이름은 `phase`로 해서 구분한다.

### 3.3 멈춤 분류와 지시

멈춤은 단계와 따로 표시한다. 아래 분류는 화면과 인계 문서에 보여 주는 이름이다. `unit.halt`에는 가운데 열의 값을 적는다. 기존 `stopped_reason` 값은 그대로 쓰고, 새 값은 `decision`, `stop-after`, `interrupt` 세 개다.

| 표시 분류 | 해당하는 값 | 모니터 표시 | 풀리는 조건 |
|---|---|---|---|
| 결정 대기 | `decision`(답이 없는 결정 요청이 있다) | 호출 벨, 분홍 | 사용자가 답한다 |
| 사용자 정지 | `stop-after`, `interrupt`(적용된 지시가 있다). 상태표의 `보류` | 문 옆 표지판 | 사용자가 계속을 지시한다 |
| 단위 막힘 | `blocked:<단위>`. 상태표의 `blocked` | 상자에 오류 표시 | 사용자가 원인을 정리한 뒤 재개한다 |
| 환경·한도 | `limit:iterations`, `limit:duration`, `expired`, `judge-fail`, `scope`, `fix-cap`, `rotate-uncertain`, `rotate-failed`, `worker-alive` | 사무실 오류 표시 | 원인을 해소한 뒤 재개한다 |

- `stopped_reason`의 `rotate`(정상 교체)와 `done`(완료)은 멈춤이 아니다. 표시하지 않는다.

지시의 종류:

| 지시 | 기계 값 | 적용 시점 |
|---|---|---|
| 메시지 | `message` | 계획자의 다음 차례 |
| 단위 후 정지 | `stop-after` | 지금 단위가 끝난 뒤. 다음 단위를 시작하지 않는다 |
| 즉시 중단 | `interrupt` | 바로. 미완료 변경은 지우지 않는다 |
| 순서 변경 | `reorder` | 다음 단위부터 |
| 계속 | `resume` | 바로 |

relay 문서의 "중단"은 auto 반복이 멈춘 모든 경우를 뜻한다. 사용자의 지시는 "즉시 중단"이라고 적어 구분한다.

### 3.4 위험 등급과 증거

단위마다 등급을 하나 적는다. 등급이 필요한 증거를 정한다. 증거 이름은 `check.result`의 종류와 1:1이다.

| 증거 | 기계 값 | 가벼움(문서·문구·설정) | 일반 | 고위험(인증·금액·데이터 삭제·공용 인터페이스) |
|---|---|---|---|---|
| 검사 명령(종료 코드 0) | `cmd` | 둘 중 하나 | 필요 | 필요 |
| 실제 확인(시험 도구가 없을 때. 사유를 적는다) | `manual` | 둘 중 하나 | 시험 도구가 없으면 대신 | 대신할 수 없다 |
| 실패 먼저 | `fail-first` | | 필요 | 필요 |
| 독립 검수 | `review` | | 필요 | 필요 |
| 변형 점검 1회 | `mutation` | | 필요 | 필요 |
| 교차 검토 | `cross-review` | | | 필요(전역 규칙) |
| 커버리지·변형 도구(변경 파일만) | `coverage` | | | 도구가 있으면 필요 |
| UI 검수(화면이 있을 때) | `ui-review` | 묶어서 한 번 | 필요 | 필요 |

- "잡을 결함"은 증거가 아니라 완료 기준의 한 줄이다. 계획 파일에 적는다.
- 시험 도구가 없어 실제 확인으로 대신한 일반 등급 단위에는 실패 먼저와 변형 점검을 요구하지 않는다. 시험이 없기 때문이다.
- 검수에서 완료를 막는 지적은 "필수 수정"뿐이다(5.4절). 지적 0건을 요구하지 않는다.
- 회차 상한은 검수 종류마다 2회다(첫 검수 1회, 재검수 1회). 넘으면 결정 요청으로 올린다.

### 3.5 이름 짓는 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 단위 ID | `U<번호>`. 보정 단위는 `U<번호>-fix<회차>` | `U3`, `U7-fix1` |
| 이벤트 종류 | `<대상>.<동작>`, 영문 소문자 | `unit.phase` |
| 새로 만드는 기계 값 | 영문 소문자와 하이픈. 화면과 문서에는 한국어 표시명을 쓴다. 기존 `stopped_reason` 값과 단위 ID는 원래 형식을 따른다 | `stop-after` → 단위 후 정지 |
| 사람이 읽는 글(사유, 질문) | 한국어 | |
| 스크립트와 하위 명령 | 영문 동사. 호출은 `<스크립트> <하위 명령> <HANDOFF.md> [인자]` | `eval-goal.sh state <HANDOFF.md> set …` |
| 환경변수 | `<스크립트 이름>_<이름>`, 대문자 | `ROTATE_KIND` |
| 모델 값 | 하네스가 보고한 ID 그대로 | `claude-fable-5-2` |
| relay 산출물 | `docs/relay/<plan>/` 아래 `PLAN.md`, `HANDOFF.md`, `goal/` | |
| 계획·설계 문서 | `docs/plans/<주제>-plan.md`. 스킬 설계는 `references/DESIGN-<주제>.md` | |
| 문서 형식 | 줄표를 쓰지 않는다. 날짜는 `YYYY-MM-DD`. 확정하지 않은 값에는 "(안)"을 붙인다. 사용자가 정할 항목은 "정해야 할 것" 절에 모은다 | |

## 4. 기록

### 4.1 이벤트 파일

- 위치(안): `<프로젝트>/.mmcode/events.jsonl`. git에 넣지 않는다.
- 한 줄에 이벤트 하나. 추가만 하고 고치지 않는다. 상태가 바뀌면 새 이벤트를 쓴다.
- 현재 상태는 이 파일을 처음부터 읽어 계산한다.

```json
{"ts":"2026-11-15T10:20:00+09:00","type":"unit.phase","plan":"orchestration","unit":"U2",
 "actor":{"terminal":"t3d","harness":"claude-code","model":"claude-fable-5-2","effort":"high"},
 "data":{"from":"build","to":"verify"}}
```

| 이벤트 | 내용 | 쓰는 쪽 |
|---|---|---|
| `plan.approve` | 계획 파일 경로와 해시. 사용자가 단위 표와 완료 기준을 승인했다는 기록 | 계획자 |
| `unit.phase` | 단위, 이전 단계, 다음 단계, 되돌아갈 때의 사유 | 단계 전환 명령 |
| `unit.halt` / `unit.resume` | 멈춤의 기계 값(3.3) | 단계 전환 명령 |
| `unit.commit` | 단위, 저장소, 해시 또는 `없음(변경 없음)` | 단계 전환 명령 |
| `check.result` | 종류(3.4의 기계 값), 통과 여부, 명령(실제 확인이면 사유), 증거 파일 경로 | 검사 실행 |
| `decision.ask` / `decision.answer` | 질문, 추천안, 막힌 단위 / 답 | 계획자 / 모니터 또는 계획자 |
| `directive.received` | 지시의 종류(3.3)와 내용 | 모니터 또는 계획자 |
| `directive.applied` / `directive.rejected` | 적용 결과. 거부할 때는 사유 | 단계 전환 명령, 훅, 계획자 |
| `session.start` / `session.stop` | 터미널, 하네스, 세션을 시작할 때의 모델과 effort, 세션 연번 | 세션 교체, 세션 시작 훅 |

- 지시를 적용하다가 사용자의 판단이 필요하면 거부한 쪽이 `directive.rejected`를 쓴다. `decision.ask`는 계획자가 다음 차례에 올린다.
- 턴마다의 도구 호출과 하위 에이전트는 이벤트 파일에 적지 않는다. 모니터가 세션 대화 파일에서 읽는다.

### 4.2 다른 파일과의 관계

| 파일 | 역할 | 정본인 범위 |
|---|---|---|
| `PLAN.md` | 단위 표, 완료 기준, 위험 등급, 완료 조건 | 무엇을 할지 |
| `events.jsonl` | 일어난 일과 단계 | 무슨 일이 일어났는지 |

| `goal/state.json` | auto 모드의 git 작업 상태(워크트리, 브랜치, 반복 수) | git 작업 |

| 세션 대화 파일 | 도구 호출, 턴별 모델, 하위 에이전트 | 하네스가 쓴다. 읽기만 한다 |

- 세션 대화 파일의 위치는 `~/.claude/projects/<프로젝트>/<세션>.jsonl`과 `<세션>/subagents/agent-*.jsonl`이다. 메시지마다 `model`, `tool_use`, `timestamp`, `isSidechain`, `agentId`가 있다(2026-11-15 파일을 열어 확인). 공개 규격이 아니므로 읽는 코드를 한 곳에 모은다.
- 인계 문서에서 생성하는 절은 상태표와 결정 대기열이다. 목표, 이월, 확인된 실패, 종료 시 제거 절은 계획자가 손으로 쓴다.

### 4.4 지시의 적용

1. 모니터가 `directive.received`를 쓴다.
2. 단위 후 정지: 단계 전환 명령이 다음 단위를 구현으로 옮기기 전에 열린 지시를 읽고 거부한다. `directive.applied`를 쓴다.
3. 즉시 중단: 도구 호출 전 훅이 열린 지시를 읽고 호출을 막는다. 모니터는 계획자 터미널에 `hc interrupt`도 보낸다. 멈춘 것을 확인한 쪽이 `directive.applied`를 쓴다.
4. 계속: 모니터가 `directive.received`를 쓰고 계획자 터미널에 `hc send`로 재개를 알린다. 계획자는 기록을 읽고 멈춘 지점에서 이어 간다. 그 터미널이 끝나 있으면 세션 교체와 같은 방법으로 새 세션을 띄운다.
5. 별도 제어 파일을 두지 않는다. 열린 지시는 기록에서 계산한다.

## 5. 완료 기준과 증거

근거는 2026-10-21에 쓴 `DESIGN-evidence.md`다. 그 문서의 장치를 3절에 연결한다. 다시 설계하지 않는다. 그 설계는 아직 스킬에 반영되지 않았다(U3).

### 5.1 완료 기준

- 단위마다 시나리오로 적는다: 조건, 행동, 기대 결과, 잡을 결함. 시나리오마다 검사를 하나 연결한다.
- 검사는 검사 명령이 기본이다. 시험 도구가 없는 프로젝트와 가벼움 등급은 실제 확인으로 대신하고 사유를 적는다(plan 4절의 기존 규칙). 고위험 등급은 대신할 수 없다. 검사 수단이 없으면 결정 요청으로 올린다.
- 형식은 `make-verifier`의 기능 지도를 재사용한다. 새 도구를 들이지 않는다.
- 사용자는 계획을 시작할 때 계획 파일을 한 번 승인한다. 지금 relay의 시작 확인과 같은 시점이다. 승인 단계를 더하지 않는다.
- 승인 뒤에 완료 기준을 바꾸면 결정 요청으로 올린다.

### 5.2 시험 증거 세 가지

1. 잡을 결함: 이 시험이 어떤 결함을 잡는지 계획 때 적는다.
2. 실패 먼저: 구현 전에 시험이 실패하는 것을 기록한다.
3. 변형 점검: 검수자가 잡을 결함 하나를 직접 넣어 시험이 실패하는지 1회 확인한다.

### 5.3 커버리지, 변형 도구, CRAP

- 프로젝트에 도구가 이미 있을 때만 쓴다. 고위험 등급에서 변경한 파일 범위로 돌린다.
- CRAP 점수는 합격 조건으로 쓰지 않는다. 점수가 높은 함수를 골라 시험을 요구하는 순위표로 쓴다. 합격 조건으로 쓰면 수치를 맞추려는 의미 없는 시험이 생긴다.

### 5.4 UI 검수

입력: 완료 기준, 화면 주소 또는 실행 방법, 지원 화면 크기, 변경 범위, 디자인 기준. 작성자의 대화는 전달하지 않는다.

1. UI 전문가가 실제 화면의 정보 위계, 가독성, 정렬, 일관성, 조작 편의, 상태 안내를 본다.
2. 독립 QA가 핵심 행동, 실패·빈 상태, 키보드, 지원 화면 크기를 직접 조작한다.
3. 계획자가 중복을 제거하고 근거를 열어 본 뒤 수정 범위를 정한다.
4. 수정한 부분과 영향받는 흐름만 다시 검수한다.

UI 전문가와 독립 QA의 첫 검수를 합쳐 1회차로 센다.

지적의 등급은 모든 검수에 똑같이 쓴다.

- 필수 수정: 요구 불충족, 재현되는 오류, 주요 조작 불가. 완료를 막는다.
- 이번 개선: 계획자가 채택 여부와 이유를 기록한다. 채택한 것만 완료 전에 고친다.
- 후속 제안: 완료를 막지 않는다.

## 6. 사람의 자리

사람이 하는 일은 세 가지다.

1. **승인**: 계획을 시작할 때 계획 파일(단위 표, 완료 기준, 위험 등급).
2. **결정**: 기계가 정하지 못하는 것. 결정 요청마다 질문, 추천안, 영향, 막힌 단위, 그동안 가능한 작업을 적는다. 막힌 단위가 많은 순으로 보여 준다.
3. **지시**: 3.3절의 다섯 가지.

- 결정을 기다리는 동안 막히지 않은 단위는 계속 진행한다.
- 순서 변경은 다음 단위부터 적용한다. 진행 중인 작업을 버리지 않는다.
- 즉시 중단 버튼은 누른 뒤 한 번 더 확인한다. 조작 실수를 막는 확인이고 승인 단계가 아니다.
- 커밋·푸시·배포의 승인은 기존 전역 규칙과 프로젝트 규칙을 따른다. 이 계획은 포괄 승인이 아니다.
- 열린 결정 요청과 지시는 기록에 있으므로 세션이 바뀌어도 남는다.

## 7. 실행과 재개

- 계획자 1개가 계획, 위임, 통합을 맡는다. 큰 단위에만 일꾼 1명을 쓴다. 검수자와 UI 전문가는 필요한 단계에서 새 맥락으로 띄운다.
- 재개: 새 세션은 생성된 인계 문서와 결정 대기열, 열린 지시만 읽는다. 이전 로그를 다시 읽지 않는다.
- 실행 중인 단위가 있으면 실제 상태(git, 터미널)를 먼저 조회한다. idle이나 프로세스 종료만으로 완료로 판정하지 않는다.
- 검증 뒤에 코드가 바뀌면 관련 검사만 다시 한다.
- 자신이 만든 터미널만 관리한다. 다른 세션과 공유 서버를 종료하지 않는다.
- 환경: Herdr.app. 터미널은 `hc`, 창은 `herdr-app`이 다룬다. 판정은 `HC_TERMINAL_ID`로 한다.
- 작업을 시작하기 전에 같은 저장소에서 일하는 다른 세션이 있는지 `hc ls`의 작업 폴더로 확인한다(2026-11-15에 두 세션이 같은 `rotate.sh` 전환을 동시에 진행했다).

### 7.1 실행 수준

사람이 얼마나 지켜보는지에 따라 세 수준을 둔다. 세 수준 모두 같은 단계 전환 명령과 같은 기록을 쓴다.

| 수준 | 사람이 하는 일 | 지금 |
|---|---|---|
| 수동 | 계획 승인. 단위마다 커밋 확인 | relay 일반 모드 |
| 단위 자동 | 계획과 완료 조건을 직접 쓰고 1회 승인. 끝난 뒤 종료 처리 | relay `auto`(실제 무인 반복은 아직 돌려 보지 않았다) |
| 계획 자동(안) | 요청 한 줄. 계획자가 미리 찾은 결정에 한 번에 답하고 계획 파일을 1회 승인. 그 뒤로는 완료 보고만 읽는다 | 없음. U6에서 만든다 |

계획 자동의 흐름(안). 2026-11-15 사용자 지정: 결정이 필요한 부분을 계획 단계에서 모두 찾아 계획에 넣고, 완성본까지 멈추지 않는다.

1. 계획자가 저장소를 조사해 계획 파일 초안을 쓴다(단위 표, 완료 기준, 위험 등급, 완료 조건, 경계).
2. **결정 사전 점검**: 계획자가 단위마다 실행 중에 사람에게 물어야 할 지점을 찾는다. 점검 목록은 아래에 있다.
3. 검수자가 새 맥락에서 초안을 한 번 읽고 빠진 결정을 찾는다. 1회만 한다.
4. 계획자가 찾은 결정을 추천안과 함께 한 번에 묻는다. 답을 계획 파일의 "사전 결정" 절에 적는다.
5. 사용자가 계획 파일을 승인한다. 이 시점이 유일한 승인이다.
6. 단위 자동과 같은 반복을 돈다. 세션 교체와 통합 검수를 거쳐 완료 보고까지 사람을 기다리지 않는다.
7. 완료 보고에 완료한 단위, 계획자가 실행 중에 정한 결정, 교차 검토로 정한 결정, 남긴 단위를 적는다.

결정 사전 점검 목록:

- 요구가 두 가지 이상으로 읽히는 곳.
- 설계 선택: 데이터 모델, 공용 인터페이스, 화면 흐름, UI 방향.
- 고위험 등급 단위와 권위 관문 영역(relay R15 ②)에 닿는 단위의 처리 방법.
- 새 의존성, 비용, 외부 서비스 사용.
- 범위: 건드리지 않을 파일, 커밋 자동 승인 범위.
- 단위가 실패했을 때의 선택: 대체 방법을 쓸지, 그 단위를 남기고 계속할지.

실행 중에 새 결정이 생기면(사전 점검이 놓친 것) relay R15 ①의 판단 사다리를 쓴다. 맨 앞에 사전 결정을 둔다.

1. 사전 결정에 답이 있으면 따른다.
2. 디스크 증거나 기록에 같은 질문의 답이 있으면 따른다.
3. 범위 안이고 되돌릴 수 있는 판단이면 계획자가 정한다. `decision.ask`와 `decision.answer`를 기록하고 답한 쪽을 계획자로 적는다.
4. 그 밖은 사용자의 결정이 필요한 판단이다. 계획자와 종류가 다른 에이전트 2종 이상에게 교차 검토를 맡긴다(2026-11-16 사용자 지정. 계획자가 claude면 codex와 agy). 질문, 선택지, 근거 파일을 주고 따로 답하게 한다. 계획자가 고른 안은 밝히지 않는다(동의 쪽으로 쏠리는 것을 막는다). 검토자는 근거 파일과 줄을 적는다. 근거가 없는 답은 의견으로 세지 않는다.
5. 세 의견(계획자, 검토자 2종) 가운데 둘 이상이 같으면 그 답으로 진행한다. `decision.ask`, 검토 결과(`check.result`의 `cross-review`), `decision.answer`(답한 쪽: 교차 검토)를 기록한다.
6. 세 의견이 모두 다르거나 검토자 2종을 띄우지 못하면 그 단위만 `blocked`로 남기고 나머지 단위를 끝까지 진행한다. 전체 반복은 멈추지 않는다.

- 이 사다리는 단위 자동과 계획 자동에 적용한다. 사람이 지켜보는 수동 수준에서는 4번에서 사용자에게 묻는다.
- 교차 검토의 회차 상한은 2다(3.4절). 검토 터미널은 기존 절차(`hc run`, 결과 파일, 끝나면 정리)를 따른다.
- 권한 경계의 결정 대기 항목(푸시, 파괴적 명령 등)은 교차 검토로 넘지 않는다.
- 완료 보고에 교차 검토로 정한 결정을 모두 적는다. 사용자가 뒤에 뒤집을 수 있게 되돌리는 방법을 함께 적는다.

지키는 것:

- 승인 없는 시작은 만들지 않는다. 완료 기준을 사람이 승인하지 않으면 1절의 문장이 성립하지 않는다.
- 사전 결정은 증거를 줄이지 않는다. 고위험 단위는 3.4절의 고위험 열에 있는 증거를 모두 낸다.
- 금액·인증·공개 인터페이스·데이터 이전·화면 느낌의 코드 수정은 허용한다. 그 영역에서 설계 선택이 갈리면 사전 결정을 따른다. 사전 결정에 없으면 계획자가 사다리 3번으로 정하지 않고 4번(교차 검토)으로 간다.
- 권한은 아래 권한 경계를 따른다. 완성본은 통합 검수를 통과한 로컬 커밋이다.
- 목표는 결정 대기로 멈추는 횟수 0이다. 환경·한도 멈춤(3.3절)은 사전 결정으로 없애지 못한다. 그때는 이유를 기록하고 정확한 지점에서 재개한다.
- 경계(최대 시간, 최대 반복, 일꾼 제한)를 넘으면 멈춘다. 같은 실패가 반복되면 원인을 다시 보고, 풀리지 않으면 그 단위를 남긴다.
- 먼저 단위 자동을 실제 작은 계획에 한 번 돌려 본다. 그 결과를 보고 계획 자동을 만든다.

권한 경계. 2026-11-15 사용자 지정: 완성에 필요한 권한은 모두 허용한다. `git push`와 시스템에 치명적인 명령은 사용자의 결정을 기다린다.

기준은 두 가지다. 그 계획의 작업 폴더(단위마다 만드는 격리 워크트리) 안인가. git으로 되돌릴 수 있는가. 둘 다 맞으면 묻지 않는다.

| 구분 | 내용 |
|---|---|
| 허용(묻지 않는다) | 작업 폴더 안의 읽기·편집·생성·삭제. 빌드, lint, 로컬 시험, 로컬 서버. 프로젝트 안의 의존성 설치. 로컬 커밋과 대상 브랜치로의 `--ff-only` 머지(계획 승인에 적힌 자동 승인 범위). 자신이 만든 작업 폴더와 터미널의 생성·정리 |
| 결정 대기 | `git push`, PR, 배포, 외부 전송. 파괴적 git(`reset --hard`, `clean`, 강제 푸시, 브랜치 삭제). 작업 폴더 밖의 쓰기·삭제(공유 폴더의 미커밋 변경 포함). 전역 설정, 권한, 자격증명 변경. `sudo`와 전역 설치. 실제 데이터에 대한 실행(운영 DB, 사용자 데이터, 데이터 이전 실행). 비용 발생. 다른 세션의 터미널·프로세스 종료 |

- 결정 대기 항목은 시도하지 않는다. `decision.ask`를 기록하고, 그 단위만 남기고 계속한다.
- 푸시처럼 마지막에 하는 일은 완료 보고에 모아 한 번에 묻는다. 사용자가 기다리는 시점은 끝 한 번이다.
- 계획자의 판단만으로 지키지 않는다. 하네스의 거부·확인 규칙(지금 전역 설정은 파괴적 git을 막고 푸시는 묻는다)과 일꾼의 샌드박스(codex `workspace-write`)를 그대로 둔다. 권한 확인을 통째로 끄는 실행 방식은 쓰지 않는다.
- 미확인: 무인 실행 중에 하네스가 확인 창을 띄우는 명령의 목록. 확인 창이 뜨면 세션 전체가 기다린다. 단위 자동을 한 번 돌려 볼 때 이 목록을 만들고, 허용 구분에 있는 명령만 프로젝트 설정의 허용 목록에 넣는다.

## 9. 구현 순서

가장 얇은 한 바퀴를 먼저 만든다. 그다음에 부품을 두껍게 한다. 단위가 끝날 때마다 실제 일 하나에 써 본다.

| 단위 | 내용 | 완료 기준 |
|---|---|---|
| U1 | 환경: `rotate.sh`와 `pair`가 `hc`·`herdr-app`에서 동작 | 가짜 실행 파일을 쓰는 시험 통과 |
| U2 | 얇은 한 바퀴: 이벤트 파일, 단계 전환 명령, 검사 결과 기록, 인계 문서 상태표 생성 | 단위 하나가 대기에서 완료까지 간다. 검사 결과가 없으면 전환을 거부한다 |

  - 만든다: 상태표의 선택 열 `등급`(가벼움, 일반, 고위험)과 `화면`(✔, ✘). `phase.sh`가 등급에 맞는 증거(3.4절)가 없으면 전환을 거부한다. `fail-first` 검사는 명령이 실패해야 통과다. 계획·relay 문서와 템플릿에 잡을 결함, 실패 먼저, 변형 점검, 통과 기준(필수 수정 없음, 회차 상한 2)을 적는다. 낱말을 3.1절에 맞춘다.

5. 세션 교체 뒤 중복 실행 없이 재개한다.

## 10. 운영 원칙

- 기존 구조와 검사 도구를 재사용한다. 가상의 예외 대비, 선제적 일반화, 새 승인 단계를 더하지 않는다.
- 등급에 맞는 검사만 한다. 시험 개수를 늘리는 것이 목적이 아니다. 사람이 읽던 일을 기계 검사로 옮기는 것이 목적이다.
- 종료 조건은 완료 기준 충족과 필수 수정 해결이다.
- 한 번도 실행하지 않은 기능은 초안이다. 초안에 검토를 더하지 않고 먼저 실행한다.
- 측정하지 못한 값은 "미측정"으로 표시한다.
- 역할을 상시 세션으로 고정하지 않는다. 독립 기능 3개 이상을 자주 동시에 진행하게 되면 다시 검토한다.

모델이 좋아지면 지울 것과 남길 것:

| 지울 것 | 남길 것 |
|---|---|
| 역할 지시문, 단계별 절차 | 이벤트 파일 |
| 세션 교체 규칙(relay R7) | 완료 기준과 증거 |
| 모델 등급표 | 승인 경계 |
| 인계 문서 손 편집 | 결정 대기열, 모니터 |
